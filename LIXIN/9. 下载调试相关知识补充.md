# 一.下载（以keil为例）

在 `Project → Options for Target` 中，有三个选项卡必须正确配置。

### 1. Target 选项卡 — 定义芯片内存布局

| 配置项 | 含义 | 示例（STM32F103C8） |
| :--- | :--- | :--- |
| **IROM1 Start / Size** | 内部 Flash 起始地址和大小 | `0x08000000` / `0x10000` (64KB) |
| **IRAM1 Start / Size** | 内部 SRAM 起始地址和大小 | `0x20000000` / `0x5000` (20KB) |

> **作用**：告诉链接器（Linker）将程序放在 Flash 的哪个位置，变量放在 RAM 的哪个位置。配置错误会导致程序无法运行。

### 2. Debug 选项卡 — 选择调试器

| 配置项 | 设置 |
| :--- | :--- |
| **Use** | 勾选，并从右侧下拉列表选择实际使用的调试器（如 `ST-Link Debugger` 或 `J-LINK / J-Trace Cortex`） |

点击右侧 **`Settings`** 按钮进入子配置：
- **Port**：选择 `SW`（SWD 两线协议）或 `JTAG`，通常选 `SW`。
- **Max Clock**：通信速度，首次连接可设为 1MHz 以确保稳定。

### 3. Utilities 选项卡 — 配置 Flash 烧录算法（核心）


点击 `Settings` 进入 **Flash Download Setup** 界面，这里有两个关键配置：

| 配置项 | 作用 | 如何填写 |
| :--- | :--- | :--- |
| **RAM for Algorithm** | 指定一块 RAM 区域，用于存放 Flash Loader 代码 | **Start** 填 `0x20000000`（SRAM 起始地址），**Size** 填 `0x1000`（4KB，一般足够） |
| **Programming Algorithm** | 选择针对当前芯片的 Flash 烧录算法（.FLM 文件） | 点击 `Add`，在列表中找到匹配的算法，如 `STM32F10x Med-density Flash` |

> **注意**：`Download to Flash` 复选框必须勾选，否则点击调试时不会自动烧录程序。

---


无论是点击 `Download (F8)` 还是 `Start/Stop Debug Session (Ctrl+F5)`，烧录 Flash 的过程完全相同。

### 5. 面试精简版回答模板

> **问**：在 Keil 中点击下载按钮后发生了什么？  
> **答**：  
> 首先，编译链接生成 `.axf` 文件。  
> 然后调试器通过 SWD 连接芯片，暂停 CPU，并把 `Programming Algorithm` 中指定的 Flash Loader 加载到 `RAM for Algorithm` 配置的 RAM 区域中运行。  
> Flash Loader 负责擦除对应扇区，并从 `.axf` 文件中逐页读取数据写入 Flash。  
> 烧写完成后芯片复位，PC 跳转到 `0x08000000` 执行用户程序。

### 6. 常见配置错误速查

| 错误提示 | 可能原因 | 解决方法 |
| :--- | :--- | :--- |
| `No Algorithm Found` | `Programming Algorithm` 未添加或选错 | 在 `Flash Download` 中添加正确 `.FLM` 文件 |
| `Cannot Load Flash Programming Algorithm` | `RAM for Algorithm` 地址或大小配置错误 | 确认 Start 为 SRAM 起始地址，Size 不小于 0x1000 |
| `Flash Timeout` | SWD 通信速度过高或不稳定 | 在 `Debug → Settings` 中降低 `Max Clock` 到 1MHz |
| `Error: Flash Download Failed - Cortex-M3` | 芯片被写保护或选项字节错误 | 使用 J-Flash 或 STM32CubeProgrammer 解除读保护 |

# 二. 面试问题
## 1. 侵入式调试和非侵入式调试的区别

**回答：**
![](assets/9.%20下载调试相关知识补充/file-20260419174152338.png)

![](assets/9.%20下载调试相关知识补充/file-20260419180747697.png)
侵入式调试（Invasive Debug）是指调试过程中会**暂停或改变**CPU/程序的正常执行流程的调试方式。典型操作包括：设置断点暂停程序、单步执行、访问/修改寄存器和内存、复位处理器等。侵入式调试通过JTAG或SWD接口连接目标芯片，调试器会占用芯片内部的调试总线（如AHB-AP），可能干扰正常的程序流。

非侵入式调试（Non-invasive Debug）是指调试过程中**不停止、不修改**处理器状态的调试方式，仅仅是观察程序的运行。典型操作包括：指令跟踪（ETM）、数据跟踪（DWT）、性能监测（PMU）、采样PC指针等。这些操作通过芯片内部的CoreSight调试组件完成，数据被复制后通过SWO引脚输出，不占用CPU时间，不干扰AHB/APB总线。

| 对比维度 | 侵入式调试 | 非侵入式调试 |
|---------|-----------|-------------|
| 是否停止CPU | 是 | 否 |
| 是否修改程序流 | 是 | 否 |
| 典型手段 | 断点、单步、内存读写 | Trace跟踪、PMU统计 |
| 对时序系统的影响 | 大（可能改变执行时序） | 极小 |
| 硬件依赖 | JTAG/SWD | CoreSight/SWO |

**面试官为什么要问这个问题？**

嵌入式系统中很多Bug是**时序敏感**的。比如电机控制、通信协议等场景中，一旦接上调试器、打断点，程序执行时序发生变化，Bug就"消失"了。面试官希望考察：

- **你是否遇到过"接上仿真器Bug就不见了"的情况？** 这说明你理解侵入式调试会干扰程序时序。
- **你是否知道Trace等非侵入式手段？** 很多嵌入式工程师只会用断点调试，不了解CoreSight、ETM、ITM等硬件调试组件的价值。
- **工程意义：** 在产品已部署的现场环境下，无法接入调试器，需要使用非侵入式手段（如日志记录、硬件Trace）来捕获偶发问题。理解两种调试方式的差异，有助于在实际工程中选择合适的调试策略。


## 2. Flash Loader概念及作用

**回答：**

Flash Loader是一个**小型程序**，在烧录阶段被下载到MCU的RAM中运行，其作用是**协助完成对Flash存储器的编程（擦除、写入、校验）**。Flash Loader通常包含两部分：GPIO和Flash接口的初始化配置，以及Flash的烧录算法。

在STM32生态中，Flash Loader有两种常见形式：
1. **STM32CubeProgrammer自带的Flash Loader**：用于通过调试器（如ST-Link）烧录内部Flash或外部Flash。烧录过程分为两个阶段——第一阶段将Flash Loader和待烧录数据加载到SRAM中，第二阶段由Flash Loader执行实际的Flash编程操作。
2. **Flash Loader Demonstrator**：ST官方提供的上位机工具，通过UART/USB与MCU的Bootloader通信，实现ISP方式烧录。

**面试官为什么要问这个问题？**

这个问题有很强的工程背景，涉及多个实际痛点：

- **理解烧录底层原理**：很多初学者只知道点击"Download"按钮，但不清楚背后发生了什么。理解Flash Loader的"两阶段烧录"机制，说明你懂得烧录的本质是把算法下到RAM中运行再去烧Flash。
- **外部Flash的烧录需求**：产品中经常需要外挂SPI Flash来存储图片、字库等资源，烧录时不能用内部Flash的算法，需要自己编写或适配外部Flash Loader。面试官可能想考察你是否有量产烧录的经验。
- **量产烧录场景**：在大批量生产中，需要配合烧录器厂商制作专用的烧录算法（.FLM文件），本质上就是在写Flash Loader。


## 3. 单片机有几种boot模式，它们的区别？

**回答：**

以STM32为例，通过BOOT0和BOOT1两个引脚的配置，芯片在上电复位后可以选择从**三种不同的存储介质**启动：

| BOOT1 | BOOT0 | 启动模式 | 启动地址 | 说明 |
|-------|-------|---------|---------|------|
| X | 0 | 主Flash启动 | 0x0800 0000 | 正常的工作模式，运行用户烧录的程序 |
| 0 | 1 | 系统存储器启动 | 0x1FFF 0000 | 运行出厂固化的Bootloader（ISP），可通过串口下载程序 |
| 1 | 1 | 内置SRAM启动 | 0x2000 0000 | 从RAM启动，用于快速调试或特殊诊断 |



三种模式的区别：
- **主Flash启动**：最常用的模式，芯片正常工作时使用。断电后程序不丢失。
- **系统存储器启动**：STM32芯片出厂时ST在系统存储器中固化了一段Bootloader程序（ROM区，用户无法修改），支持通过UART、USB、CAN等接口下载程序，即**ISP方式**。
- **SRAM启动**：程序直接在RAM中运行。由于RAM掉电丢失，这种模式主要用于**调试**（避免反复擦写Flash）或**故障诊断**。

**面试官为什么要问这个问题？**

这个问题考察的是**工程经验**，几乎每个嵌入式工程师都会遇到：

- **Flash被锁死的处理**：如果在代码中误操作了Flash选项字节或把JTAG/SWD引脚配置成普通GPIO，会导致无法通过调试器连接芯片。这时需要将BOOT0拉高，从系统存储器启动，才能重新烧录程序"救砖"。
- **理解芯片上电流程**：知道芯片怎么决定从哪里启动，才能理解中断向量表的映射机制（0x08000000被映射到0地址）。
- **生产场景**：在产线上，需要通过ISP方式烧录程序时，需要控制BOOT引脚电平。不理解这个就做不了量产方案。


## 4. STM32中的程序一般在RAM还是FLASH里运行？（拓展：冯诺依曼架构和哈佛架构）

**回答：**

STM32的程序**一般在Flash中直接运行**（XIP，eXecute In Place），而不是像PC那样先加载到RAM再运行。

原因在于架构差异：STM32属于**哈佛架构**（更准确地说是"优化的哈佛架构"或"哈佛式冯·诺依曼模型"）：

| 架构类型 | 指令/数据总线 | 程序运行方式 | 典型代表 |
|---------|-------------|-------------|---------|
| 冯·诺依曼架构 | 指令和数据共用一套总线 | 程序从外存加载到RAM中执行 | PC（x86）、部分ARM A系列 |
| 哈佛架构 | 指令总线和数据总线分开 | 指令直接从Flash取指执行 | 51单片机、ARM Cortex-M系列（如STM32） |

在STM32中，CPU通过**I-Code总线**从Flash读取指令，同时通过**D-Code总线**访问SRAM中的数据进行运算，两条总线可以并行工作，因此可以在Flash中直接执行程序，同时访问RAM中的数据。

**补充说明**：
- STM32的程序**也可以**在RAM中运行。调试时可以手动将代码下载到SRAM并从SRAM启动，优点是调试速度快（避免反复擦写Flash），缺点是需要考虑SRAM容量。
- 部分高性能场景（如DSP算法）会将关键代码段复制到RAM中运行以获得更高执行速度。

**面试官为什么要问这个问题？**

这个问题考察的是对**处理器架构底层理解**，关联多个工程场景：

- **内存分配规划**：知道程序在Flash运行、数据在RAM，才能正确理解分散加载（Scatter Loading）和链接脚本，知道哪些变量在Flash（const常量）、哪些在RAM（全局变量、堆栈）。
- **Bootloader设计**：升级时新固件需要先写入Flash，然后跳转执行。如果不理解Flash XIP机制，就不懂跳转地址为什么是Flash地址而非RAM地址。
- **性能优化**：在某些场景下需要把代码从Flash复制到RAM运行以获得更高速度（如运行在零等待状态的SRAM比Flash更快），需要知道为什么可以这样做。
- **选型考量**：理解哈佛架构的特点，有助于选择适合的MCU架构。


## 5. 单片机一般使用NOR Flash还是NAND Flash？为什么？

**回答：**

单片机**一般使用NOR Flash**作为内部程序存储器。原因如下：

**1. NOR Flash支持XIP（片上执行）**
NOR Flash可以像SRAM一样按地址随机读取，CPU能直接从NOR Flash中取指令执行，无需先将代码复制到RAM。这对于存储空间有限的单片机至关重要，可以节省SRAM容量。

**2. NOR Flash读取速度更快，可靠性更高**
NOR Flash的读取性能接近SRAM，且数据可靠性更高（不需要ECC纠错），这对于存放程序代码非常关键。NAND Flash的读取是以块为单位进行的（通常一次读512字节），随机访问慢，且存在位翻转问题，必须依赖ECC纠错机制。

**3. NAND Flash适合大容量数据存储**
NAND Flash的擦除和写入速度快、单位容量成本低，适合存储日志、多媒体等大量数据，但不适合直接执行代码。手机、SSD等设备用NAND Flash当"硬盘"，但仍需要一块小的NOR Flash来存放启动代码。

**对比总结**：

| 对比维度 | NOR Flash | NAND Flash |
|---------|-----------|------------|
| 读取方式 | 按字节随机读取 | 按页/块读取 |
| XIP支持 | ✅ 支持 | ❌ 不支持 |
| 容量 | 较小（MB级别） | 较大（GB级别） |
| 写入速度 | 较慢 | 较快 |
| 成本 | 较高 | 较低（大容量时） |
| 擦写寿命 | ~10万次 | ~3000-1万次 |
| 典型应用 | 单片机程序存储 | 固态硬盘、SD卡、手机存储 |

**面试官为什么要问这个问题？**

- **硬件选型能力**：产品设计时，需要根据需求选择合适的存储方案。如果只是存固件代码，选NOR Flash（或MCU内置Flash）；如果需要存大量日志或音视频文件，考虑外挂NAND Flash或SD卡。
- **Bootloader设计**：如果用了NAND Flash存放固件，上电后需要先将代码从NAND复制到RAM才能执行，这和从NOR Flash直接启动是完全不同的启动流程。
- **成本和可靠性权衡**：NOR Flash单价比NAND高，但可靠性更好。理解两者的特性，才能在产品成本和可靠性之间做出合理选择。
- **理解芯片内部Flash的本质**：MCU内置的Flash本质上就是NOR Flash。知道了这一点，才能理解为什么代码可以直接在Flash运行、为什么Flash有擦写寿命、为什么写Flash前必须先擦除扇区。
