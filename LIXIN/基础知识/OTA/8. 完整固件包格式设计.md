# 固件包格式设计

> 所有安全机制（加密、哈希、签名、版本控制）最终都落地为一个固件包格式。Bootloader 收到这个包后按预定顺序解析和验证。

实际项目中固件不是裸的 `.bin`，会有一个头部：

```c
typedef struct {
    uint8_t  magic[4];      // "FWPK" 魔数，标识这是固件包
    uint32_t version;       // 固件版本号，防降级
    uint32_t firmware_size; // 原始固件大小（PKCS7填充前），解密后SHA256用此长度
    uint8_t  iv[16];        // AES-CBC 的 IV
    uint8_t  sha256[32];    // 解密后固件的 SHA256
    uint8_t  signature[64]; // ECC-P256 对 SHA256 摘要的签名（r=32字节 + s=32字节）
    uint32_t header_crc;    // 头部自身的 CRC32，防头部损坏
} __attribute__((packed)) FirmwareHeader_t;

// 完整固件包：
// [FirmwareHeader_t 128字节][加密的固件数据...]

// ⚠️ firmware_size 容易误解：
// 如果 firmware.bin 是 100KB，PKCS7 填充后变成 100032 字节再加密。
// 但 header 里存的必须是 100000（原始大小），SHA256 也是对原始 100000 字节算的。
// 接收方解密后要先按 firmware_size 截断（去掉PKCS7填充），再做 SHA256。
```

### 各字段说明

| 字段 | 大小 | 谁写入 | 用途 |
|------|------|--------|------|
| `magic` | 4B | PC | 快速识别固件包，防止把随机数据当固件处理 |
| `version` | 4B | PC | [[9. 固件验证流程实现\|防降级]]检查 |
| `firmware_size` | 4B | PC | 解密后按此长度截断（去PKCS7填充），也是SHA256的输入长度 |
| `iv[16]` | 16B | PC | AES-CBC 解密的前置条件，PC 端随机生成 |
| `sha256[32]` | 32B | PC | 解密后固件的 [[3. 哈希算法（解决完整性）\|SHA256]]，用于完整性校验 |
| `signature[64]` | 64B | PC | 对 sha256 摘要的 [[5. 非对称加密原理（解决真实性）\|ECC 签名]]，用于真实性验证 |
| `header_crc` | 4B | PC | 头部自身的 CRC32，接收方先验证这个确保头部没损坏 |

### 验证顺序为什么是这个样子

设备端验证必须先从不需要解密的字段开始，逐步深入：

```
魔数 → 版本号 → 头部CRC → AES解密 → SHA256 → ECC验签
 ↑                ↑                    ↑              ↑
 轻量检查          轻量检查              重量计算        重量计算
 (memcmp 4字节)   (整数比较)            (遍历整个固件)   (椭圆曲线运算)
```

如果把 AES 解密放在最前面，一个损坏的固件包会白白浪费 CPU 时间做解密。
