# YModem 协议原理与使用

Ymodem 是一个**文件传输协议**，专门设计用来可靠地传输二进制文件。OTA 场景里用它把新固件从上位机传到 STM32。

> 在 OTA 流程中的位置：YModem 位于 [[1. OTA 固件升级完整流程|总览]] 的**传输层**，负责把 [[8. 完整固件包格式设计|固件包]]（头部+密文）从 PC 端可靠地传到设备端。它只保证传输正确，不负责安全——安全由 [[3. 哈希算法|哈希]]、[[4. AES 原理|AES]]、[[5. 非对称加密原理|签名]] 保证。

---

## 为什么用 Ymodem 而不是自定义协议

自定义协议你要自己处理：分包、重传、校验、文件大小传递。Ymodem 把这些全做好了，而且有现成的上位机工具支持（SecureCRT、XShell、minicom），不需要自己写上位机。

---

## 帧结构

YModem 使用两种数据包格式：

**128字节包（SOH）**

```
┌─────┬──────┬────────┬──────────────┬────────┐
│ SOH │ 包号 │ 包号取反 │  128字节数据  │ CRC16  │
│0x01 │ 1字节│  1字节  │              │ 2字节   │
└─────┴──────┴────────┴──────────────┴────────┘
  总共 133 字节
```

**1024字节包（STX）**

```
┌─────┬──────┬────────┬───────────────┬────────┐
│ STX │ 包号 │ 包号取反 │  1024字节数据  │ CRC16  │
│0x02 │ 1字节│  1字节  │               │ 2字节   │
└─────┴──────┴────────┴───────────────┴────────┘
  总共 1029 字节
```

Ymodem 固定用 1024 字节包，比老版 Xmodem 的 128 字节快很多。

---

## 关键字节定义

```c
#define SOH    0x01   // 128  字节包头
#define STX    0x02   // 1024 字节包头
#define EOT    0x04   // 文件传输结束
#define ACK    0x06   // 确认（收到了，继续）
#define NAK    0x15   // 否认（出错了，重传）
#define CA     0x18   // 取消传输（需连发两个）
#define CRC16  0x43   // 字符'C'，请求使用 CRC 模式
```

## 传输流程

```
上位机（发送方）          STM32（接收方）

                    <─── 'C'         接收方准备好，发'C'请求开始

  包0（文件名包）   ────>             包含文件名和文件大小
  
                    <─── ACK         收到包0
                    <─── 'C'         请求数据

  包1（数据包）     ────>             第1个1024字节
                    <─── ACK
  包2（数据包）     ────>             第2个1024字节
                    <─── ACK

  ...
  
  EOT               ────>             文件发完了
                    <─── NAK         要求确认
  EOT               ────>             再发一次确认
                    <─── ACK
  空文件名包        ────>             结束整个传输会话
                    <─── ACK
```

## Block 0（文件信息帧）详解

Block 0 是 YModem 相对于 XModem 最重要的扩展：

```text
数据段内容（128字节）：
┌─────────────────┬────┬───────────────────────────────────────────┬───────────────┐
│ 文件名           │ \0 │ 文件信息字符串                              │ 剩余填 0x00    │
│ "firmware.bin"  │    │ "102400 1752073441 "                      │ 0x00 0x00 ... │
└─────────────────┴────┴───────────────────────────────────────────┴───────────────┘
```

- 文件名以 `\0` 结尾
- 文件信息字符串内部结构（**空格分隔**）：
	  * "102400"      ← 文件大小（十进制ASCII），**空格结尾**
	  * "1752073441"  ← 修改时间（八进制Unix时间戳），**空格结尾**
- 剩余字节填充 `\0`
- **空 Block 0**（全0）表示批量传输结束

STM32 收到包0后从这里解析出文件大小，用来：

- 验证固件大小不超过 App 分区
- 知道什么时候传完了

## 核心函数解析（参考ST 官方 AN2557 应用笔记附带的 ymodem.c）

### Receive_Byte —— 带超时单字节接收


```c
static int32_t Receive_Byte(uint8_t *c, uint32_t timeout)
{
    while (timeout-- > 0)
    {
        if (SerialKeyPressed(c) == 1)
            return 0;   // 收到返回 0
    }
    return -1;          // 超时返回 -1
}
```

> ⚠️ **移植注意**：timeout 是循环次数，不是毫秒。移植时改为基于 `HAL_GetTick()` 的真实超时：
> 
> ```c
> uint32_t start = HAL_GetTick();
> while (HAL_GetTick() - start < timeout_ms) {
>     if (uart_rx_available()) { *c = uart_rx_read(); return 0; }
> }
> return -1;
> ```

---

### Receive_Packet —— 接收一个完整包

**返回值：**

```
 0  正常（收到数据包 / EOT / CA CA）
 1  用户按键中止（收到 ABORT1/ABORT2）
-1  超时或包格式错误
```

**length 输出参数含义：**

```
length > 0   正常数据包，值为包大小（128 或 1024）
length = 0   收到 EOT，文件传输结束
length = -1  收到 CA CA，发送方主动取消
```

**处理逻辑：**

```c
// 1. 等第一个字节，判断包类型
switch (c) {
    case SOH: packet_size = 128;   break;
    case STX: packet_size = 1024;  break;
    case EOT: return 0;             // length = 0，上层判断结束
    case CA:
        // CA CA 双字节才算取消，防止单字节误触发
        if (第二个字节也是CA) { *length = -1; return 0; }
        return -1;
    case ABORT1/ABORT2: return 1;  // 用户中止
    default: return -1;
}

// 2. 继续收完整包（包号 + 包号取反 + 数据 + CRC）
// PACKET_OVERHEAD = 包号(1) + 包号取反(1) + CRC(2) = 4
for (i = 1; i < (packet_size + PACKET_OVERHEAD); i++)
    Receive_Byte(data + i, timeout);

// 3. 验证包序号
// 包号 XOR 包号取反必须等于 0xFF
if (data[SEQNO] != ((data[SEQNO_COMP] ^ 0xFF) & 0xFF))
    return -1;
```

> ⚠️ **缺陷**：这里收了 CRC 字节但**没有验证**，需要移植时补上。

---

### Ymodem_Receive —— 接收主函数

**双层循环结构：**

```
外层循环：管整个 session（支持连续传多个文件）
    内层循环：管单个文件的接收
        switch(Receive_Packet 返回值)
            case  0：正常，再按 length 细分处理
            case  1：用户中止，发 CA CA 退出
            case -1：超时/错误，计数，超限则退出
```

**session_begin 的作用（设计亮点）：**

```c
if (session_begin > 0)
    errors++;
```

传输还没开始时超时**不计入错误计数**。 原因：接收方启动后持续发 'C' 等待，发送方可能还没准备好， 这段等待期间的超时不应该被算作传输错误。

**包0处理（文件信息包）：**

```c
if (packets_received == 0)
{
    // 解析文件名
    file_ptr = packet_data + PACKET_HEADER;  // 跳过3字节包头
    拷贝文件名直到 \0;

    // 解析文件大小（ASCII字符串转整数）
    file_ptr++;  // 跳过 \0
    拷贝文件大小字符串直到空格;
    Str2Int(file_size, &size);  // "102400" → 102400

    // 检查固件大小
    if (size > FLASH_SIZE) { 发 CA CA; return -1; }

    // 提前擦除 Flash（根据文件大小计算需要擦几页）
    NbrOfPage = FLASH_PagesMask(size);
    for (...) FLASH_ErasePage(...);

    Send_Byte(ACK);    // 确认包0
    Send_Byte(CRC16);  // 请求用 CRC 模式
}
```

**数据包处理（写 Flash）：**

```c
else
{
    memcpy(buf_ptr, packet_data + PACKET_HEADER, packet_length);

    // 按4字节写入 Flash，写完立刻回读验证
    for (j = 0; j < packet_length && FlashDestination < AppAddr + size; j += 4)
    {
        FLASH_ProgramWord(FlashDestination, *(uint32_t*)RamSource);

        // 写入后立刻验证（发现问题及时终止，不等全部写完）
        if (*(uint32_t*)FlashDestination != *(uint32_t*)RamSource) {
            Send_Byte(CA); Send_Byte(CA);
            return -2;  // Flash 写入验证失败
        }
        FlashDestination += 4;
        RamSource += 4;
    }
    Send_Byte(ACK);
}
```

**返回值含义：**

```
size > 0  成功，返回文件大小（字节）
0         发送方取消 或 超过最大错误次数退出
-1        固件大小超过 Flash 空间
-2        Flash 写入验证失败
-3        用户中止
```

### CRC16 实现

Ymodem 使用 CRC-16/CCITT，多项式 0x1021，**末尾需额外补两个 0x00 字节**：

```c
uint16_t UpdateCRC16(uint16_t crcIn, uint8_t byte)
{
    uint32_t crc = crcIn;
    uint32_t in  = byte | 0x100;  // bit8 作循环结束标志
    do {
        crc <<= 1;
        in  <<= 1;
        if (in  & 0x100)   crc++;          // 数据 bit 为 1
        if (crc & 0x10000) crc ^= 0x1021;  // 多项式
    } while (!(in & 0x10000));             // 8个bit处理完毕
    return crc & 0xFFFF;
}

uint16_t Cal_CRC16(const uint8_t *data, uint32_t size)
{
    uint32_t crc = 0;
	const uint8_t* dataEnd = data+size;
    while (data < dataEnd)
        crc = UpdateCRC16(crc, *data++);
    // ⚠️ 末尾补两个 0，Ymodem 协议规定，与普通 CRC16 不同
    crc = UpdateCRC16(crc, 0);
    crc = UpdateCRC16(crc, 0);
    return crc & 0xFFFF;
}
```

> ⚠️ 不能直接用普通 CRC16 库替换，末尾补 0 是 Ymodem 特有要求。

## 移植到 STM32F4 必须修改的地方

|问题|原代码|修改方法|
|---|---|---|
|**CRC 未验证**|收了 CRC 但没调用验证|在 `Receive_Packet` 或 `Ymodem_Receive` 里补上 `Cal_CRC16` 验证|
|**超时不准确**|`timeout` 是循环次数|改为 `HAL_GetTick()` 计时|
|**Flash 操作 F1 专用**|`FLASH_ErasePage` / `FLASH_ProgramWord`|F4 改用 `HAL_FLASH_Unlock` + `HAL_FLASHEx_Erase` + `HAL_FLASH_Program`|
|**全局变量**|`FlashDestination` 等为全局|封装进结构体，FreeRTOS 环境下避免竞争|

### F4 Flash 操作替换示例

```c
// 解锁
HAL_FLASH_Unlock();

// 擦除（F4 按扇区擦除，不是按页）
FLASH_EraseInitTypeDef erase = {
    .TypeErase    = FLASH_TYPEERASE_SECTORS,
    .Sector       = FLASH_SECTOR_2,   // 根据 App 起始地址确定扇区号
    .NbSectors    = 需要擦除的扇区数,
    .VoltageRange = FLASH_VOLTAGE_RANGE_3
};
uint32_t sectorError;
HAL_FLASHEx_Erase(&erase, &sectorError);

// 写入（F4 支持按字节/半字/字/双字写）
HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, address, data);

// 加锁
HAL_FLASH_Lock();
```

## 与 OTA Bootloader 的结合

```
上电
  ↓
Bootloader 检查升级标志（RTC 备份寄存器 / Flash 参数区）
  │
  ├─ 有升级标志
  │     ↓
  │   清除升级标志
  │     ↓
  │   Ymodem_Receive() 接收固件
  │     ↓
  │   校验完整性（CRC 全包校验）
  │     ↓
  │   跳转 App
  │
  └─ 无升级标志 → 直接跳转 App
```

**升级标志写入（App 里触发）：**

```c
// 写 RTC 备份寄存器，断电不丢失
HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR0, 0xDEADBEEF);
HAL_NVIC_SystemReset();  // 复位，进入 Bootloader
```

**升级标志检查（Bootloader 里）：**

```c
if (HAL_RTCEx_BKUPRead(&hrtc, RTC_BKP_DR0) == 0xDEADBEEF) {
    HAL_RTCEx_BKUPWrite(&hrtc, RTC_BKP_DR0, 0x00000000);
    Ymodem_Receive(buf);
}
```

## 常见坑点

1. **Block 0 的 ACK 后必须再等 'C'** 才能发第一个数据块，很多实现漏掉这步
2. **EOT 需要两次确认**：第一次 NAK，第二次才 ACK
3. **末尾填充**：最后一块不足时用 `0x1A`（Ctrl-Z）或 `0x00` 填充，接收方需按实际文件大小截断
4. **超时与重试**：发送方对每个 ACK 应有超时重传机制（通常重试10次）
5. **块序号回绕**：块号是单字节，255之后回绕到0（不是1）

## 边界条件与进阶话题

---

### 1. 接收方窗口与流控

YModem 是**停等协议（Stop-and-Wait）**，每块都要等 ACK 才发下一块，没有滑动窗口。在高延迟链路上吞吐量很差，但串口 bootloader 场景延迟极低，问题不大。如果你的 UART 波特率较低（如 115200），1KB 块传输时间约 90ms，加上 ACK 往返，实际速率远低于理论值。

---

### 2. CAN 取消机制

发送方或接收方都可以通过连发**两个 CAN（0x18）**中止传输。接收方收到 CAN 后应擦除已写入的不完整固件，否则会留下损坏的 Flash 内容。很多实现只处理正常流程，忽略了 CAN 的清理逻辑。

---

### 3. Flash 擦除时序问题

STM32 IAP 中，接收 Block 0 拿到文件大小后才知道要擦多少个扇区。**擦除期间不能响应 UART**，如果擦除耗时较长（F4 的某些扇区擦除需要 1~2 秒），发送方可能超时重传甚至放弃。

解决方式：

- 在发送 Block 0 的 ACK **之前**完成擦除
- 或者在握手阶段就擦除整个 App 区域（不等文件大小）

---

### 4. 块序号验证

收到数据包后要校验：

```
buf[1] + buf[2] == 0xFF
// 等价写法: (buf[1] ^ buf[2]) == 0xFF
// 在8bit下，~x = 0xFF - x，所以 ~buf[1] + buf[1] ≡ 0xFF (mod 256)
```

即块号与其反码之和必须为 0xFF，这是独立于 CRC 的第二道校验，不能省略。很多移植代码只检查 CRC，跳过了这步。

---

### 5. 重传限制

接收方发 NAK 请求重传时，发送方最多重传 **10 次**（标准规定），超过后发送方应发 CAN 中止。接收方也应对连续 NAK 计数，防止死循环。

---

### 6. 实际工具端行为差异

不同 PC 端工具实现有细节差异：

|工具|注意事项|
|---|---|
|minicom / sz|标准实现，行为可预期|
|SecureCRT|Block 0 后的第二个 'C' 有时有延迟|
|Tera Term|YModem 实现较标准，IAP 常用|
|自定义 Python|用 `pyserial` 手写时注意串口缓冲区刷新|

---

### 7. 多文件批传结束判断

批量传输时，**空 Block 0（128字节全0）** 是结束信号，接收方要明确区分：

- `buf[3] == 0`（文件名首字节为0）→ 批次结束
- 否则 → 新文件开始

漏判这个条件会导致接收方把结束帧当成新文件处理。

---

总体而言，YModem 协议本身不复杂，坑主要集中在**边界条件处理**和**Flash 操作时序**上，建议直接参考 ST 的 AN2557 实现作为基础再修改，比从零写更可靠。
