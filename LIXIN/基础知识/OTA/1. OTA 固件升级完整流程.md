# OTA 固件升级完整流程

## 整体架构

一个完整的 OTA 固件升级系统，从 PC 端打包到 STM32 设备端验证写入，分为五个层次，每层解决不同的问题：

```
┌──────────────────────────────────────────────────────────────────────┐
│                        OTA 完整流程                                   │
│                                                                      │
│  PC 端（打包发布）                          STM32 端（接收验证）         │
│  ════════════════                         ════════════════════════   │
│                                                                      │
│  // PC端操作顺序：②→④→⑥→⑧→⑨                                         │
│  // STM32端操作顺序：⑩→⑦→⑥SHA256→⑤ECDSA验签→⑫→⑬                     │
│  // 注意：STM32必须先AES解密，再自己算SHA256，再把SHA256传给ECDSA验证    │
│                                                                      │
│  ① firmware.bin 编译出来                                             │
│       ↓                                                              │
│  ② SHA256 计算摘要                                                   │
│     （完整性 [[3. 哈希算法（解决完整性）]]）                              │
│       ↓                                                              │
│  ④ ECDSA 私钥签名（对②的摘要签名）──────→  ⑤ ECDSA 公钥验签            │
│     （真实性 [[5. ECDSA数字签名原理（解决真实性）]]）  （hash是输入！）     │
│       ↓                                                              │
│  ⑥ AES-CBC 加密 ─────────────────────→  ⑦ AES 解密                  │
│     （保密性 [[4. AES 原理（解决保密性）]]）   （得到明文固件）            │
│       ↓                                                              │
│  ⑧ 打包成固件包（头部明文+密文载荷）                                    │
│     [[8. 完整固件包格式设计]]                                          │
│       ↓                                                              │
│  ⑨ YModem 发送 ──────────────────────→  ⑩ YModem 接收               │
│     [[2. ymodem协议]]                      （可靠传输固件包）           │
│                                                ↓                    │
│                                          ⑪ 魔数/版本/CRC检查          │
│                                          ⑦ AES 解密→固件明文          │
│                                          ③ SHA256（STM32自己算）      │
│                                          ⑤ ECDSA验签（传入SHA256）    │
│                                          [[9. 固件验证流程实现]]       │
│                                                ↓                    │
│                                          ⑫ 写入 Flash               │
│                                                ↓                    │
│                                          ⑬ 跳转 App                 │
└──────────────────────────────────────────────────────────────────────┘
```

## 五层安全模型

OTA 的安全是分层防护，每层解决不同的问题：

| 层次 | 解决的问题 | 技术手段 | 对应笔记 |
|------|-----------|---------|---------|
| **传输层** | 数据怎么可靠地传过去 | YModem 协议（分包、校验、重传） | [[2. ymodem协议]] |
| **完整性** | 数据有没有被篡改/损坏 | SHA256 哈希 | [[3. 哈希算法（解决完整性）]] |
| **保密性** | 固件内容不能被读走 | AES-CBC 对称加密 | [[4. AES 原理（解决保密性）]] |
| **真实性** | 固件确实是我发的 | ECDSA 数字签名 | [[5. ECDSA数字签名原理（解决真实性）]] |
| **防回滚** | 不能刷回旧版本固件 | 版本号递增检查 | [[9. 固件验证流程实现]] |

### 为什么是这套技术选型

- **YModem 而不是自定义协议**：有现成上位机工具（SecureCRT、minicom），不需要自己写 PC 端
- **AES 而不是其他对称加密**：硬件加速支持好，STM32F4 有 CRYP 外设
- **ECDSA 而不是 RSA**：256bit ECDSA ≈ 3072bit RSA 安全强度，嵌入式上计算量和密钥尺寸小得多
- **SHA256 而不是 MD5**：MD5 已被破解，可人为构造碰撞

## 完整固件包结构

所有安全机制最终落地为一个固件包格式（详见 [[8. 完整固件包格式设计]]）：

```
┌──────────────────────────────────────┐
│  FirmwareHeader（128字节，明文不加密） │
│  magic | version | fw_size | iv[16]  │
│  sha256[32] | signature[64] | crc    │
├──────────────────────────────────────┤
│  加密的固件数据（AES-CBC 密文）         │
└──────────────────────────────────────┘
```

**头部为什么不加密**：头部里的 IV 是 AES 解密的必要条件，如果头部加密就需要先解密才能得到 IV，形成死循环。头部所有字段本身都不需要保密（详见 [[8. 完整固件包格式设计]]）。

**信任链**：签名是对 SHA256 签的，SHA256 是解密后算的——攻击者要伪造固件，必须同时攻破 ECDSA 签名和 AES 加密两层。

## 设备端验证流程（Bootloader）

```
收到固件包
    ↓
① 检查魔数 "FWPK"     → 是固件包吗？                （[[8. 完整固件包格式设计]]）
    ↓
② 检查版本号          → 比当前版本高？（防降级）        （[[9. 固件验证流程实现]]）
    ↓
③ 验证头部 CRC        → 头部完整没被损坏？             （[[8. 完整固件包格式设计]]）
    ↓
④ AES-CBC 解密        → 拿到固件明文                   （[[4. AES 原理（解决保密性）]]）
    ↓
⑤ 按 firmware_size 截断，去掉 PKCS7 填充
    ↓
⑥ SHA256 固件明文     → 自己计算摘要                   （[[3. 哈希算法（解决完整性）]]）
    ↓
⑦ 比对头部 sha256     → 摘要一致？（完整性校验）
    ↓
⑧ ECDSA 公钥验签      → 传入⑥算出的 SHA256，验证签名有效？  （[[5. ECDSA数字签名原理（解决真实性）]]）
    ↓                   ⚠️ SHA256 是 ECDSA 验证的数学输入，不是用来"比对"的
⑨ 写入 Flash → 跳转 App
```

> ⚠️ **ECDSA 验签的关键**：步骤⑥算出的 SHA256 必须作为参数传给 ECDSA 验证函数。
> 这和 RSA 不同（RSA 可以从签名里解出哈希），ECDSA 的数学要求哈希作为输入参与运算。
> 详见 [[5. ECDSA数字签名原理（解决真实性）]]。

**验证顺序的设计考量**：魔数、版本号、头部 CRC 成本最低放最前面，快速拒绝非法固件。
AES 解密和 SHA256 是重量级计算，放后面只对通过前置检查的固件执行。

## 工具链对应关系

| 环节 | PC 端（打包） | STM32 端（验证） |
|------|-------------|-----------------|
| 哈希 | `openssl dgst -sha256` | mbedTLS `sha256.h` |
| 加密 | `openssl enc -aes-128-cbc` | mbedTLS `aes.h` |
| 签名 | `openssl dgst -sha256 -sign ec_private.pem` | mbedTLS `ecdsa.h`（hash 作为输入）|
| 传输 | lrzsz-sz + YModem | YModem 接收（AN2557 移植）|

PC 端用 OpenSSL 命令行（[[7. 使用OpenSSL命令实现上述]]），STM32 端用 mbedTLS（[[6. 使用mbedTLS实现上述]]）。

## YModem 在整体流程中的位置

YModem（[[2. ymodem协议]]）只负责**传输**，传输的内容是完整的固件包（明文头部 + AES 密文），不是裸的 `.bin`。

YModem 自身的 CRC16 只能检测传输误码，不能检测恶意篡改——SHA256 + ECDSA 签名才是安全保障。
