# OTA 固件升级完整流程

## 整体架构

一个完整的 OTA 固件升级系统，从 PC 端打包到 STM32 设备端验证写入，分为五个层次，每层解决不同的问题：

```
┌──────────────────────────────────────────────────┐
│                OTA 完整流程                        │
│                                                    │
│  PC 端（打包发布）          STM32 端（接收验证）     │
│  ════════════════          ════════════════════     │
│                                                    │
│  ① firmware.bin 编译出来                           │
│       ↓                                            │
│  ② SHA256 计算摘要 ────────────────→ ③ 比对摘要    │
│     （完整性 [[3. 哈希算法（解决完整性）]]）  （验证未被篡改）│
│       ↓                                            │
│  ④ ECC 私钥签名 ──────────────────→ ⑤ 公钥验签    │
│     （真实性 [[5. 非对称加密原理（解决真实性）]]） （验证来源可信）│
│       ↓                                            │
│  ⑥ AES-CBC 加密 ──────────────────→ ⑦ AES 解密    │
│     （保密性 [[4. AES 原理（解决保密性）]]）  （防止固件泄露）│
│       ↓                                            │
│  ⑧ 打包成固件包 [[8. 完整固件包格式设计]]           │
│       ↓                                            │
│  ⑨ YModem 发送 ───────────────────→ ⑩ YModem 接收 │
│     [[2. ymodem协议]]                  （可靠传输）  │
│                                            ↓       │
│                                      ⑪ 防降级检查  │
│                                      [[9. 防降级攻击实现]]│
│                                            ↓       │
│                                      ⑫ 写入 Flash  │
│                                            ↓       │
│                                      ⑬ 跳转 App    │
└──────────────────────────────────────────────────┘
```

> 括号内的 `[[文件名]]` 是 Obsidian 双向链接，指向同目录下的详细笔记。

## 五层安全模型

OTA 的安全不是单一手段，而是分层防护：

| 层次 | 解决的问题 | 技术手段 | 对应笔记 |
|------|-----------|---------|---------|
| **传输层** | 数据怎么可靠地传过去 | YModem 协议（分包、校验、重传） | [[2. ymodem协议]] |
| **完整性** | 数据有没有被篡改/损坏 | SHA256 哈希 | [[3. 哈希算法（解决完整性）]] |
| **保密性** | 固件不能被别人读走 | AES-CBC 对称加密 | [[4. AES 原理（解决保密性）]] |
| **真实性** | 固件确实是我发的 | ECC 数字签名 | [[5. 非对称加密原理（解决真实性）]] |
| **防回滚** | 不能刷回旧版本固件 | 版本号递增检查 | [[9. 防降级攻击实现]] |

### 为什么是这套技术选型

- **YModem 而不是自定义协议**：有现成的上位机工具（SecureCRT、minicom），不需要自己写 PC 端
- **AES 而不是其他对称加密**：硬件加速支持好，STM32F4 有 CRYP 外设
- **ECC 而不是 RSA**：256bit ECC ≈ 3072bit RSA 安全强度，嵌入式上计算量小得多
- **SHA256 而不是 MD5**：MD5 已被破解，可人为构造碰撞

## 完整固件包结构

所有安全机制最终落地为一个固件包格式（详见 [[8. 完整固件包格式设计]]）：

```
┌──────────────────┬─────────────────────────┐
│  FirmwareHeader  │  加密的固件数据          │
│  (128 字节)       │  (AES-CBC 密文)         │
└──────────────────┴─────────────────────────┘
```

头部包含：
- **magic** — 魔数 "FWPK"，标识这是一个有效的固件包
- **version** — 版本号，防降级攻击
- **iv[16]** — AES-CBC 的初始向量
- **sha256[32]** — 解密后固件的 SHA256（用于完整性校验）
- **signature[64]** — 对 sha256 的 ECC 签名（用于真实性验证）
- **header_crc** — 头部自身的 CRC32，防头部损坏

关键的信任链：**签名是对 SHA256 签的，SHA256 是解密后算的**——所以要伪造合法固件，攻击者需要同时攻破签名和加密两层。

## 设备端验证流程（Bootloader）

```
收到固件包
    ↓
① 检查魔数 "FWPK"  → 确实是固件包？（[[8. 完整固件包格式设计]]）
    ↓
② 检查版本号       → 比当前版本高？（[[9. 防降级攻击实现]]）
    ↓
③ 验证头部 CRC     → 头部完整？（[[8. 完整固件包格式设计]]）
    ↓
④ AES-CBC 解密     → 拿到固件明文（[[4. AES 原理（解决保密性）]]）
    ↓
⑤ 按 firmware_size 截断，去掉 PKCS7 填充
    ↓
⑥ SHA256 固件明文  → 计算摘要（[[3. 哈希算法（解决完整性）]]）
    ↓
⑦ 对比头部的 sha256 → 一致？（完整性校验）
    ↓
⑧ ECC 公钥验签     → 签名有效？（真实性校验，[[5. 非对称加密原理（解决真实性）]]）
    ↓
⑨ 写入 Flash → 跳转 App
```

**验证顺序的设计考量**：魔数、版本号、头部 CRC 放在最前面，因为它们是成本最低的检查（不需要解密、不需要哈希），能快速拒绝明显非法的固件。AES 解密和 SHA256 是计算量最大的步骤，放在后面只对通过前置检查的固件执行。

## 工具链对应关系

| 环节 | PC 端（打包） | STM32 端（验证） |
|------|-------------|-----------------|
| 哈希 | `openssl dgst -sha256` | mbedTLS `sha256.h` |
| 加密 | `openssl enc -aes-128-cbc` | mbedTLS `aes.h` |
| 签名 | `openssl dgst -sign` | mbedTLS `ecdsa.h` |
| 传输 | YModem 发送（SecureCRT/minicom） | YModem 接收（AN2557 移植） |

PC 端用 OpenSSL 命令行（[[7. 使用OpenSSL命令]]），STM32 端用 mbedTLS 库（[[6. 使用mbedTLS]]）。

## YModem 在整体流程中的位置

YModem（[[2. ymodem协议]]）只负责**传输**，它不关心传输的内容是什么。在 OTA 流程中，YModem 传输的 payload 就是上面设计的固件包（头部+密文）。

YModem 自身的 CRC16 校验只能检测传输错误（位翻转），不能检测恶意篡改。所以 YModem 层之上的 SHA256 和数字签名是不可替代的安全保障。
