### 1. 什么是 HardFault？
HardFault 是 Cortex-M 系列处理器中优先级最高的异常之一（固定优先级 -1，高于所有可配置优先级的中断）。它是“最终捕获器”：

- 当其他可配置的 Fault（如 MemManage Fault、Bus Fault、Usage Fault）发生，但对应的 Handler 未启用(默认**未使能**)、或在 Fault Handler 中再次出错时，会**升级（escalate）** 到 HardFault。
- 直接触发 HardFault 的情况：严重错误，如取指失败、栈损坏等。
- 一旦进入 HardFault，程序基本“跑飞”了，通常表现为死机、复位循环或卡在 while(1) 中。

**为什么会发生？** 它表示处理器检测到无法恢复的错误，继续执行会更危险。

### 2. 常见触发原因
- **栈溢出（Stack Overflow）**：局部变量太大、中断嵌套太深、RTOS 任务栈不够。
- **数组越界 / 野指针 / 空指针解引用**：访问非法内存地址。
- **内存访问违例**：访问未映射的地址、外设未使能就访问、Flash/ SRAM 边界外。
- **非对齐访问（Unaligned Access）**：某些 Cortex-M（如 M0）不支持非 4 字节对齐访问；M4/M7 可通过配置启用检查。
- **无效指令或除零**（需启用 UsageFault）。
- **中断/异常处理出错**：在中断中调用不安全的函数（如带浮点但未使能 FPU）。
- **硬件问题**：外部总线错误、Flash 读写错误等。
- **调试相关**：断点、调试器连接问题。

### 3. 如何调试 HardFault（最实用方法）
#### 方法一：Keil/IAR/CubeIDE 调试器直接看（最快）
1. 在 `HardFault_Handler()` 的 `while(1)` 处**打断点**。
2. 程序停住后，查看：
   - **LR (R14)**：判断使用 MSP 还是 PSP（0xFFFFFFF9 → MSP；0xFFFFFFFD → PSP）。
   - **SP (MSP/PSP)**：堆栈指针。
   - **PC**：出错时的指令地址（栈帧中 stacked_pc）。
   - **CFSR（Configurable Fault Status Register）**、**HFSR**、**MMFAR**、**BFAR** 等 SCB 寄存器，快速定位错误类型。
3. 查看 Call Stack，右键 “Show Caller Code” 定位到出错附近代码。

#### 方法二：增强 HardFault_Handler 自动打印信息（推荐）
在 `stm32xx_it.c` 中替换默认 Handler，加上下面代码（带详细注释）：

```c
// stm32xx_it.c
#include "stdio.h"  // 用于 printf（需重定向到串口或 SWO）

// 汇编部分：判断使用 MSP 还是 PSP，并把栈指针传给 C 函数
void HardFault_Handler(void)
{
    __asm volatile (
        "TST lr, #4 \n"          // 测试 LR 的 bit2，判断是 MSP 还是 PSP
        "ITE EQ \n"              // If-Then-Else 条件执行块（EQ 表示“相等”）
        "MRSEQ r0, MSP \n"       // 如果是 MSP，把 MSP 存到 r0
        "MRSNE r0, PSP \n"       // 如果是 PSP，把 PSP 存到 r0
        "B hard_fault_handler_c \n"  // 跳转到 C 函数处理
    );
}

// C 函数：打印栈帧和故障寄存器
void hard_fault_handler_c(uint32_t *hardfault_args)
{
    uint32_t stacked_r0  = hardfault_args[0];
    uint32_t stacked_r1  = hardfault_args[1];
    uint32_t stacked_r2  = hardfault_args[2];
    uint32_t stacked_r3  = hardfault_args[3];
    uint32_t stacked_r12 = hardfault_args[4];
    uint32_t stacked_lr  = hardfault_args[5];  // 返回地址
    uint32_t stacked_pc  = hardfault_args[6];  // 出错指令地址（关键！）
    uint32_t stacked_psr = hardfault_args[7];

    printf("========== Hard Fault 发生！ ==========\r\n");
    printf("Stacked R0  = 0x%08X\r\n", stacked_r0);
    printf("Stacked R1  = 0x%08X\r\n", stacked_r1);
    printf("Stacked R2  = 0x%08X\r\n", stacked_r2);
    printf("Stacked R3  = 0x%08X\r\n", stacked_r3);
    printf("Stacked R12 = 0x%08X\r\n", stacked_r12);
    printf("Stacked LR  = 0x%08X\r\n", stacked_lr);   // 调用者返回地址
    printf("Stacked PC  = 0x%08X\r\n", stacked_pc);   // **出错代码位置**
    printf("Stacked PSR = 0x%08X\r\n", stacked_psr);

    // 打印故障状态寄存器
    printf("HFSR = 0x%08X\r\n", SCB->HFSR);   // Hard Fault Status
    printf("CFSR = 0x%08X\r\n", SCB->CFSR);   // Configurable Fault Status (包含 MMFSR/BFSR/UFSR)
    printf("MMFAR = 0x%08X\r\n", SCB->MMFAR); // 内存管理故障地址
    printf("BFAR = 0x%08X\r\n", SCB->BFAR);   // 总线故障地址

    // 可选：清除标志位防止重复触发
    SCB->HFSR |= (1 << 31);  // 清除 FORCED 位等

    while(1);  // 停在这里方便调试器连接
}
```
一句话总结上面代码：
> **当发生 HardFault 时，取出 CPU 自动压栈的数据 → 传给 C 函数 → 打印出错现场**

#### 方法三：使用专业工具

除了手动分析，还可以借助一些强大的开源工具来简化调试过程：
- **CmBacktrace**：一个专为 ARM Cortex-M 设计的错误追踪库。它能自动分析 `HardFault` 的上下文，并打印出完整的函数调用栈，让你一目了然地看到错误是如何一步步发生的，极大地提升了调试效率。

### 补充：
#### 相关寄存器

在 ARM Cortex-M 中：当发生异常（HardFault）时，CPU 会自动把这些寄存器**顺序**压栈：
```text
xPSR
PC
LR
R12
R3
R2
R1
R0
```
##### 1. 通用寄存器（Caller-saved 寄存器）

| 寄存器     | 你可以把它当成       | 平时在干嘛            | 出问题时你该关注啥                                                |
| ------- | ------------- | ---------------- | -------------------------------------------------------- |
| **R0**  | “第一个参数 / 返回值” | 函数第1个参数、返回值、临时变量 | ⭐ 很关键：经常是**指针**（空指针崩溃常见），若看见R0 = 0x00000000，则代表进行了空指针写操作 |
| **R1**  | “第二个参数”       | 函数第2个参数          | 看是不是传错值（比如地址错）                                           |
| **R2**  | “第三个参数”       | 同上               | 一般辅助判断                                                   |
| **R3**  | “第四个参数”       | 同上               | 一般辅助判断                                                   |
| **R12** | “编译器随手用的变量”   | 中间计算、临时寄存        | ❌ 基本不用看（除非你在做底层分析）                                       |

**这五个寄存器（R0~R3, R12）属于 “Caller-saved”**，即函数调用前调用者必须自己保存它们的值。

##### 2. 特殊寄存器（与异常高度相关）

| 寄存器      | 名称                      | 作用说明                                           | 在 HardFault 中的重要性                                  |
| -------- | ----------------------- | ---------------------------------------------- | -------------------------------------------------- |
| **LR**   | Link Register（R14）      | 存函数返回地址，也就是函数执行完要跳回的位置（BL 指令会把下一条指令地址存入 LR）    | **非常重要**如果 LR 是 0xFFFFFFxx 形式，说明这是异常返回（EXC_RETURN） |
| **PC**   | Program Counter（R15）    | 当前正在执行的指令地址，也就是“程序跑到哪儿了”                       | **⭐ 最重要**通常指向**出错的那条指令**或其下一条指令                    |
| **xPSR** | Program Status Register | 程序状态寄存器，记录“程序的当前状态”：包括条件标志、当前中断号、Thumb/ARM 模式等 | 帮助判断程序当时的运行状态，配合 PC/LR 分析异常原因，很关键                  |

##### 它们之间的联系（重点理解）

1. **PC（程序计数器）—— 出错位置的核心**
   - HardFault 发生时，压入栈的 **PC** 通常就是**导致故障的那条指令地址**（或下一条）。
   - 注意：Cortex-M 在异常入栈时做了特殊处理：硬件会修正 PC 值，把压入栈的 PC 调整为真正触发异常的指令地址
   - 同步故障（精确故障）：PC 就是真正出错的那条指令
   - 异步故障（不精确故障）：如：总线错误发生在写缓冲区（写操作延迟到后面才真正出错），这时压入的 PC 是下一条要执行的指令（或之后），无法精确指向原错误指令。

2. **LR（链接寄存器）**
   - 如果代码是正常函数调用，LR 保存返回地址。
   - 但在异常发生时，**LR 被硬件自动替换成 EXC_RETURN**（一个特殊值，如 `0xFFFFFF9`（bit[2]为0）、`0xFFFFFFFD`（bit[2]为1） 等）。
   - 通过 LR 的 bit[2] 就能判断当时用的是 MSP 还是 PSP。
   - 🔄 **补充：**
        > - 当异常发生时，处理器硬件自动执行一系列操作，其中最关键的一步就是将计算好的 `EXC_RETURN` 值存入 `LR` 寄存器。随后，当异常处理函数结束时，需要将这个特殊值从 `LR` 加载回**程序计数器（PC/R15）**，当 `PC` 接收到一个高28位全为 `1` 的值时，处理器便会将其识别为 `EXC_RETURN`，而不是一个普通的代码地址，从而启动异常返回序列, 以触发硬件自动化的返回流程。
		 > - ETURN的高28位全为1，作为硬件识别 EXC_RETURN 的特征码，只有bit[3:0]的值有特殊含义。位段如下：
		 ![](assets/8.%20HardFault/file-20260422224326542.png)
		 > - `EXC_RETURN` 主要有三个合法值，它们决定了返回后的处理器模式和所使用的堆栈。其具体含义如下：
		 ![](assets/8.%20HardFault/file-20260422224542965.png)
		 
3. xPSR（程序状态寄存器）
	**最简单的一句话总结：CPU 刚才运算结果怎么样（APSR）、当前正在处理哪个异常（IPSR）和CPU 处于什么执行状态（EPSR）**
	
	1. **bit 31~28：APSR,  Application PSR（标志位，最常用）**
	   - N（Negative）：上一次运算结果是负数吗？
	   - Z（Zero）：上一次运算结果是 0 吗？
	   - C（Carry）：有进位吗？
	   - V（Overflow）：溢出了吗？
	   
	   → 这些主要用来判断代码最后做了什么运算出问题。
	
	2. **bit 8~0：IPSR, Interrupt PSR（异常号，最重要之一）**
	   - 存着当前正在处理的**异常编号**。
	   - HardFault 的编号是 **3**。
	   - 如果 IPSR 显示是 3，就确认确实是 HardFault。
	
	3. **bit 24：T 位（Thumb 状态）**
	   - 必须一直是 **1**。
	   - 因为 Cortex-M 只认 Thumb 指令集，如果这里是 0，就说明出大问题了（通常不会出现）。
	
	4. **bit 26~25 + bit 15~10：IT 块（If-Then）**
	   - 用于条件执行指令（IT 指令块）。
	   - 一般故障时不用太关注。

#### 汇编代码讲解
- 发生 HardFault → 硬件自动压栈（到 MSP 或 PSP）并把 EXC_RETURN 放入 LR。
-  进入 `HardFault_Handler`。
-  这段汇编判断 LR 的 bit2，选出正确的 SP，放到 r0（r0作用就是放置函数的第一个参数）。
- 跳转到 C 函数进行详细故障分析
```c
__asm volatile (
    "TST lr, #4 \n"
    "ITE EQ \n"
    "MRSEQ r0, MSP \n"
    "MRSNE r0, PSP \n"
    "B hard_fault_handler_c \n"
);
```

##### 1. `TST lr, #4`
- TST 是 “Test” 指令，内部其实做的是 lr & 4，但结果不保存，只用来更新标志位（特别是 Z 标志Zero Flag）
- `lr` 是 Link Register（R14），在异常发生时，硬件会把**返回信息**（EXC_RETURN）存入 LR。
- `#4` 就是二进制的 `0b100`，即 bit2。
- **关键**：EXC_RETURN 的 bit[2] 决定使用哪个栈指针：
  - `bit2 = 0` → `(lr & 4) == 0`成立 → `Z = 1`（EQ 成立）→ 使用 **MSP**（Main Stack Pointer，主栈，通常用于中断/异常）
  - `bit2 = 1` → `(lr & 4) ！= 0`成立 → `Z = 0`（NE 成立）→  → 使用 **PSP**（Process Stack Pointer，进程栈，通常用于线程模式）

##### 2. `ITE EQ`
- **If-Then-Else** 指令（Thumb-2 特有）。
- 它告诉后面的两条指令：
  - 第一条指令在 **EQ**（相等，即 Z=1）时执行；
  - 第二条指令在 **NE**（不等，即 Z=0）时执行。

这是为了实现条件选择，非常高效（不需要分支）。

##### 3. `MRSEQ r0, MSP`
- 如果是 EQ（即使用 MSP），则把 **MSP** 的值读到 `r0` 寄存器。
- `MRS` = Move from Special Register。

##### 4. `MRSNE r0, PSP`
- 如果是 NE（即使用 PSP），则把 **PSP** 的值读到 `r0` 寄存器。
- 经过这两条指令后，**r0 里一定是当前发生 HardFault 时使用的栈指针**。

##### 5. `B hard_fault_handler_c`
- 无条件跳转到 C 函数 `hard_fault_handler_c`。
- 因为 `r0` 已经存放了栈指针，根据 ARM 的 AAPCS 调用约定，`r0` 是第一个参数，所以 C 函数可以这样定义：

```c
void hard_fault_handler_c(uint32_t *stack_frame)
{
    // stack_frame 指向压栈的寄存器内容
    // 可以打印 xPSR, PC, LR, R0~R3, R12 等
}
```
